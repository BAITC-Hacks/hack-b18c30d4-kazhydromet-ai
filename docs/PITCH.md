# «Граф денег»: сценарий на пять минут

Рабочая заготовка: расчёт и новый интерфейс ещё разрабатываются.
Перед выступлением выбрать примеры по итоговым файлам и заменить пометки
в квадратных скобках. Непроверенные обещания не произносить как результаты.

## 0:00–0:40 — пользователь и боль

«Специалисту банка по противодействию отмыванию денег известен список из 81
исходного клиента. Но в предоставленной сети уже 2 248 участников.
Нужно решить, кого проверять первым и почему. По описанию заказчика,
ручное восстановление цепочки занимает часы на один узел.
Мы готовим инструмент, который собирает признаки, предлагает роли и объясняет
приоритет проверки конкретными числами».

## 0:40–1:10 — данные и живой запуск

Запустить команду из финального README в подготовленном окружении.
Показать три созданных CSV и измеренное время.

«На входе участники, связи и отдельные переводы. Все 2 248 участников,
включая 19 без связей, должны попасть в результат. Этот прогон занял [время]
на [ноутбук]. Расчёт [после проверки: работает без внешней языковой модели]».

Если расчёт ещё идёт, показать схему из README и вернуться к файлам после
завершения. Превышение лимита расчёта нужно выявить до выступления.

## 1:10–2:10 — первый узел: почему он в приоритете

Выбрать участника из свежего top_nodes.csv, открыть по gid.
Показать входящие и исходящие связи, роль и объяснение.

«Он получил средства от [число] разных отправителей на [сумма] ₸,
а в наблюдаемой сети отправил [сумма] ₸. По правилу [название и порог из кода]
у него признаки [роль]. Поэтому мы предлагаем проверить его раньше:
[обоснование приоритета из расчёта]».

Если жюри называет произвольный gid, использовать поиск и те же поля карточки.
Не привязывать расчёт к заранее выбранному идентификатору.

## 2:10–3:00 — второй узел: другая роль

Выбрать рассчитанный пример распределения либо транзита. Сравнить с первым:
число получателей, направления потоков, суммы и количества переводов.
Временные признаки показывать только после реализации и проверки.

«Одинаковая сумма может скрывать разное поведение. Здесь [факты из карточки],
поэтому правило предлагает другую роль. Аналитик может проверить основание».

## 3:00–3:40 — третий узел: граница наших знаний

Показать узел на четвёртом колене и реализованный признак неполноты.

«У 444 участников на границе выгрузки не видны дальнейшие переводы.
Это не означает, что деньги остались у них. Мы показываем [реализованное
обозначение], чтобы не принять отсутствие данных за доказательство.
Для продолжения проверки нужны сведения о последующих переводах».

## 3:40–4:25 — результат для специалиста

Показать список приоритетов, группы и три выгрузки.

«Специалист получает список участников для проверки с объяснениями,
схему связей и описание групп. Роль — проверяемая гипотеза.
Решение о дальнейших действиях остаётся у человека».

Языкового помощника показывать только после проверки ответа по данным кейса.
При отсутствии связи продолжить показ локальных результатов.

## 4:25–5:00 — измеренный результат и следующий шаг

«На этой выборке расчёт занял [измеренное время]. Мы проверили [реальные проверки
покрытия узлов, схем файлов и объяснений]. Следующий шаг — оценить список
со специалистом и измерить время разбора одинаковых случаев с инструментом
и без него».

Не обещать установленную точность ролей: правильные ответы не размечены.
Не называть оборот преступным доходом, предотвращённым ущербом или уникальными
деньгами. Проверенный оборот выгрузки — 365 890 012,01 ₸.

## Перед выходом

- Выбрать 2–3 gid по свежему результату; записать числа, роль и правило.
- Проверить команду запуска, поиск произвольного gid и три CSV.
- Сверить фактические пороги и формулы с README.
- Записать время расчёта и характеристики ноутбука.
- Проверить интерфейс без интернета и запасной показ сохранённых результатов.
- Уложиться в пять минут на репетиции.
